## Исправления v3.16.0 — 2026-10-12

Это исходный аудит версии 3.15.3; номера строк и описание дефектов ниже относятся к commit 89f3f03. Для v3.16.0 реализованы:

- SQLite Durable Object на комнату, транзакционное слияние относительно базового снимка, идемпотентные подтверждения операций; часы клиента не выбирают победителя.
- Устойчивая очередь IndexedDB, повторная отправка после offline/ошибок/потерянного ACK, последовательное завершение и создание обходов.
- Явные конфликты с резервной копией, раздельные данные комнат, перенос legacy KV/IndexedDB без удаления оригиналов.
- Общая история с маркерами удаления, защита текущего обхода от удаления, сохранение ссылок на недоступные фото и повторная загрузка; новые фото без семидневного TTL.
- Полный precache сборки, перезагрузка без сети, локальное создание QR, корректные статусы ошибок, исправление источника и фильтрации Weekly API.
- 28 регрессионных тестов проходят. TypeScript/Vite build и Wrangler dry-run проходят. Два независимых Chromium-контекста с реальным локальным Worker/SQLite проверили обмен в обе стороны, offline edit/reload/reconnect, конфликт одного поля, завершение и следующий обход, сохранение завершённого отчёта в общей истории.

Ограничения: физические iPhone/Android и установленная PWA на реальных устройствах не проверялись. Переход уже установленного старого service worker на новую сборку не проверен браузерным тестом. Два одновременно редактирующих окна одного браузерного профиля не входят в проверенный сценарий. Production-доступ и внешняя защита не подтверждены. Опциональный EHS_SYNC_TOKEN реализован, но секрет не установлен: room-scoped авторизация/pairing остаётся отдельной работой. Без секрета или внешней защиты API остаётся открытым по коду комнаты. Существующая зависимость xlsx не заменена; выводы исходного npm audit ниже относятся к прежнему lockfile.

Обновлять необходимо оба устройства; старые API записи получают 426. Параметры развёртывания и миграции описаны в README. Актуальные тесты: `npm test`, `npm run build`, `npm run test:browser`. Не откатывать сервер к старым безусловным KV-записям после миграции.

## Исходный вывод

Текущая реализация не обеспечивает безопасное редактирование с телефона и ноутбука. Это обмен последним полным снимком одного обхода через KV, а не синхронизация базы с конфликтами, подтверждениями и устойчивой очередью. Возможны потеря правок, пропуск завершения обхода, повреждение набора фотографий и ложный индикатор успеха.

Проверены исходники клиента, Worker, IndexedDB, архив, QR-подключение, service worker, сборка и CI. Production /api/health вернул 403 из среды проверки; действующий deployment, внешние средства защиты и состояние KV не подтверждены. Рабочие комнаты/данные не запрашивались и не изменялись. Исходники приложения, GitHub и deployment не изменены.

## P1 — потеря данных / нарушение изоляции

### 1. Безусловная перезапись целого обхода

Код: src/worker/index.ts:300–354; src/hooks/useCloudSync.ts:124–148, 252–268.

Worker принимает любой JSON и выполняет put без сравнения ревизии. Поле version увеличивается только в памяти каждого клиента; сервер его не использует. Клиент сравнивает часы устройств, но не серверную ревизию и не базовую версию изменения.

Сценарий: оба устройства открыли один снимок; телефон изменил пункт A, ноутбук — B. Последняя запись целиком заменяет первую, поэтому один пункт теряется. Рассинхронизация часов может дополнительно заставить устройство отвергать актуальные данные. Одинаковый updatedAt разных изменений ошибочно дедуплицируется.

Доказательство: тест Worker принимает последовательную перезапись без конфликта. Независимые изменения не сливаются — отсутствует соответствующий код.

Исправление: серверная ревизия и атомарная проверка expectedRevision; конфликт возвращать явно и сохранять обе версии. Мерж независимых полей допустим только относительно известной общей базовой версии. Не добавлять GET-then-PUT CAS поверх KV: это не атомарная операция.

### 2. Нет устойчивой очереди и повторной отправки

Код: src/hooks/useCloudSync.ts:154–160, 188–208, 263–280, 450–493; src/App.tsx:293–329.

online/focus/poll вызывают только pull. После offline/503 последняя правка не отправляется автоматически без нового изменения, ручной отправки или перезапуска. Если push уже идёт, следующий вызов возвращает обещание старого запроса и забывает новое содержимое — даже explicit Completed или новый обход. После старого ACK выставляется synced, хотя текущее состояние ещё не отправлено.

Подтверждено тестами: offline → online без push; explicit completion потерян во время push; правка во время push не досылается, статус становится synced.

Исправление: outbox в IndexedDB; очередь по room/session; ACK конкретной ревизии/operationId; после ACK отправлять накопившиеся изменения; retry с backoff/jitter на online, foreground и временных ошибках. Завершение и создание обхода — отдельные идемпотентные операции.

### 3. Ошибка GET трактуется как пустая комната

Код: src/utils/syncApi.ts:188–216; src/hooks/useCloudSync.ts:373–435.

404, 503, timeout, неверный JSON возвращают одинаковый null. Начальная синхронизация воспринимает null как отсутствие данных и отправляет локальный снимок. Временная ошибка чтения способна вызвать перезапись существующего обхода устаревшими данными.

Подтверждено тестом: 503 превращается в null. Решение initial-sync → push следует непосредственно из ветки кода.

Исправление: различать found/notFound/offline/error/invalid; после ошибки чтения не разрешать безусловную инициализацию комнаты.

### 4. Фото теряются, восстанавливаются после удаления и попадают в другой обход

Код: src/hooks/useCloudSync.ts:284–324, 332–347, 380–398; src/App.tsx:97–164; src/hooks/useInspection.ts:29–61; src/worker/index.ts:311.

- Временный сбой GET фото удаляет ссылку из photos; тот же updatedAt затем дедуплицируется и не восстанавливает фото в UI. Следующая локальная правка может закрепить отсутствие ссылки в облаке.
- Пустой список фотографий восстанавливается из локальных фото: удаление последней фотографии не переносится корректно.
- Восстановление по item.id не проверяет совпадение session.id: фото предыдущего обхода могут попасть в новый с теми же пунктами.
- Старые/Completed-сессии архивируются до разрешения photo references. Периодический pull может повторно записывать в архив пустые url поверх ранее полных фотографий.
- Все ключи имеют TTL 7 дней; фото загружаются однократно на время работы клиента, обновление сессии TTL фото не продлевает.

Тест воспроизводит исчезновение ссылки при временной недоступности фотографии. Остальные пути подтверждены исходниками.

Исправление: сохранять unresolved references и статус загрузки, повторять загрузку независимо от ревизии сессии; явная семантика удаления; room/session scope; архивировать только с сохранением имеющихся байтов/ссылок. Retention фотографий должен соответствовать retention отчётов.

### 5. Ответ старой комнаты применяется в новой

Код: src/hooks/useCloudSync.ts:173–184, 192–193, 327–355; src/App.tsx:370–380; src/components/SyncModal.tsx:363–370.

Обычные pull не имеют AbortController/generation guard на смену комнаты. Cache/ref и in-flight push общие. После смены комнаты старый ответ может изменить новый экран. QR-handler после setSyncRoom вызывает forcePush/forcePull из старого render: замыкание ещё содержит старую комнату.

Тест: задержанный GET комнаты TEST завершён после переключения OTHER; в OTHER применяется снимок TEST.

Исправление: единый нормализованный roomId, generation token и отмена запросов; кеши/outbox разделены по комнате; QR только переключает комнату и запускает room-aware pull-first, без отправки старым замыканием.

### 6. Ложный успех синхронизации

Код: src/components/SyncModal.tsx:128–145; src/hooks/useCloudSync.ts:73, 263–268; src/utils/syncApi.ts:136–146; src/worker/index.ts:349–368.

Modal показывает «Синхронизировано в облаке» для error/pending, если navigator.onLine=true. Начальное состояние — synced до проверки сети/сервера. Ответ 200 с не-JSON HTML считается успехом. Worker без KV отвечает success:true на хранение только в памяти isolate; warning клиентом не показывается.

Два теста подтверждают acceptance HTML 200 и success:true без KV.

Исправление: строгий JSON ACK подтверждённой durable-ревизии; отсутствие KV — ошибка; все состояния UI отображать явно; pending пока текущее состояние не подтверждено.

### 7. История не синхронизируется между устройствами

Код: src/utils/syncApi.ts:96–99; src/hooks/useHistory.ts; src/hooks/useCloudSync.ts:105–121; src/worker/index.ts:300–354.

В комнате один session_<ROOM>. Архив и удаления — только локальная IndexedDB. Если ноутбук был закрыт при завершении нескольких обходов, он получает только последний снимок и не может скачать пропущенные отчёты. Отдельных серверных сущностей истории, cursor или tombstones нет.

Дополнительно useHistory.isInitialMount выставляется true, но нигде false: lightweight backup истории в localStorage никогда не обновляется. Удалённые legacy-записи могут вернуться при refreshHistory из старого localStorage. Ошибки сохранения в IndexedDB подавляются внутри helpers, поэтому вызывающий код не может отличить durable save от отказа.

Исправление: серверные записи по sessionId с ревизиями и cursor; tombstones удаления; общая outbox для создания/обновления/архивирования. IndexedDB ошибки должны возвращаться вызывающему коду.

### 8. API не проверяет доступ к комнате

Код: src/worker/index.ts:20–28, 151–178, 255–368; src/utils/syncApi.ts:84–88; src/components/SyncModal.tsx:55–60.

Worker не проверяет авторизацию; код комнаты FSE-MAIN предсказуем. X-Device-ID не аутентификация. По исходникам любой достигший endpoint клиент может читать/перезаписывать известный ключ; JSON schema и размер запроса не проверяются. QR URL уходит стороннему qrserver, room name — публичному ntfy topic.

Это вывод по приложению; наличие внешней Cloudflare Access/WAF-защиты не подтверждено. Эксплуатация production не выполнялась.

Исправление: доступ по короткоживущему pairing/invitation token и серверным room-scoped правам; QR формировать локально; валидировать payload. Клиентский deviceId использовать лишь как метаданные.

## P2 — архитектура, офлайн, дополнительная целостность

### 9. KV не обеспечивает обещанную live-синхронизацию

Worker читает/пишет один KV-ключ на комнату. Клиент debounce450ms, polling2500ms. По документации Cloudflare KV имеет eventual consistency и лимит одной записи на ключ в секунду; cache-busting query на HTTP этого не меняет. SSE передаёт лишь ping и не устраняет устаревшее чтение KV. Обещание 1–2 секунды в SyncModal не гарантируется.

Источники:
- https://developers.cloudflare.com/kv/api/write-key-value-pairs/
- https://developers.cloudflare.com/kv/concepts/how-kv-works/

Рекомендация: Durable Object на комнату с транзакционным состоянием/ревизиями и outbox на клиентах; KV оставить только для некритичных кешей. Альтернатива — D1 с атомарным условным UPDATE и явными конфликтами. Миграция должна сначала сохранить существующие снимки и локальные архивы.

### 10. Service worker не гарантирует готовность офлайн

Код: public/sw.js:5–37; vite.config.ts:18–31; src/utils/pwa.ts:79–102.

Precache содержит HTML/icons, но не сборочные JS/CSS. На первой установке эти файлы могли загрузиться до того, как SW начал контролировать страницу. skipWaiting/claim немедленно активируют новый SW и удаляют прежние кеши до загрузки всех новых bundles. Ошибка precache подавляется. Update вручную стирает кеш и unregister, а затем требует успешной сети.

Подтверждено анализом сборки: dist/assets содержит JS/CSS, которых нет в STATIC_ASSETS. Реальный offline browser test в этом аудите не выполнялся.

Исправление: build-generated precache полного asset manifest; завершение install только после успешного кеширования; контролируемая активация обновления без удаления последнего рабочего shell.

### 11. Weekly API читает другой ключ и другую структуру

Код: src/worker/index.ts:57–95; src/utils/syncApi.ts:96–99.

GET /api/reports/weekly ищет room:<ROOM>, но sync пишет session_<ROOM>. Даже при совпадении ключа требуется unwrap payload.session. Сейчас endpoint при отсутствии данных возвращает averageComplianceScore=100/GREEN и auditedDaysCount=0. start/end только отражаются в ответе, не фильтруют сессии. Это дефект данного API; не утверждается, что локальный weekly UI использует его.

### 12. CI не запускает тесты синхронизации

.github/workflows/deploy.yml выполняет npm ci + build, затем deploy hook. package.json не содержит test script. В существующих scripts нет проверки реального hook/Worker взаимодействия для перечисленных race/offline случаев.

npm audit на проверенном lockfile: 9 affected packages (7 high, 2 moderate; это не девять независимых эксплуатируемых уязвимостей). xlsx — runtime dependency с high и без fixAvailable в npm audit; остальные находки в build toolchain. Полный JSON приложен. Массовый npm audit fix --force не выполнялся.

## Воспроизводимая проверка

- npm ci: успешно.
- npm run build: успешно; TypeScript + Vite.
- audit/sync.test.ts + audit/api.test.ts: 9/9 воспроизведений дефектов успешно.
- Это characterization-тесты: PASS означает подтверждение ошибки текущего поведения, а не исправность приложения.
- React hook исполнялся с happy-dom; сеть и IndexedDB mocked; Worker — с изолированным fake KV. Физические устройства/реальное Cloudflare KV не тестировались.
- Инструменты: Node24, Vitest5, happy-dom20 из уже установленного соседнего проекта. Зависимости/package-lock приложения не изменялись.
- Эти временные characterization-тесты запускались до исправлений и не входят в актуальный regression suite; описание сохраняет результаты исходного аудита.

## Единый объём исправления

Один связанный change-set: durable room protocol с revision/CAS + idempotent operationId; IndexedDB outbox/retry; room/session isolation; фото refs/deletions/retry; серверный архив; честные состояния UI; precache; regression tests. Не лечить конкурентность дополнительными setTimeout и сравнением клиентских часов.

Приёмка: два независимых browser contexts; параллельные изменения разных и одинаковых полей; offline edit/reconnect/reload; потерянный ACK; 429/503; finish/reset во время upload; переключение комнаты с незавершённым GET; photo failure/delete; пропущенные обходы и история; clean install → offline; old SW → new build. Ни одна неподтверждённая правка не теряется, конфликт видим, synced означает ACK текущей ревизии.
